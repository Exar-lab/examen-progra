# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Spring Boot 4.0.6 service (`com.buses.examen.Progra`), Java 25, Maven. Domain: bus ticket sales for a Central American bus company headquartered in Costa Rica.

Key dependencies: Spring Data JPA + MySQL, Spring Security + OAuth2 Authorization Server, Spring Cloud Load Balancer, Bean Validation, Actuator, Lombok.

## Assignment Statement (ENUNCIADO)

- A new bus company in Central America, headquartered in Costa Rica, needs a ticket sales system.
- After buying a ticket, customers receive a unique invented code that lets them travel.
- The company offers different routes and service schedules between countries, with different prices.
- Tickets can only be bought for services within a maximum one-week purchase window.
- A person cannot buy more than 5 tickets.
- To buy, the user must be registered or register in the database with: first name, last name, passport, nationality, email, phone, card, CCV, and expiration date.
- Sessions must control access so only registered users can use protected system operations.
- After purchase, the system must emit an electronic PDF receipt with the unique ticket code and trip data such as time and route.
- The student must preload data in the database.

### Product Rules

- The ticket code is unique per ticket and should be generated by the system, not supplied by the client.
- Purchase window is inclusive: `purchaseDate <= serviceDeparture <= purchaseDate + 7 days`.
- Maximum tickets per purchase/person flow is 5.
- Card data is sensitive: do not persist raw CVV beyond the purchase/registration boundary unless the assignment explicitly requires a simplified educational model. Prefer tokenized/masked storage for production-like code.
- Session/security behavior is part of the assignment, but implement it in an application/security slice, not inside domain entities.

## Architecture

Use **Hexagonal Architecture (Ports and Adapters)** organized by feature/domain, not global technical layers.

Dependency rule: dependencies point inward. `domain` must not depend on Spring MVC, Spring Data repositories, security, web DTOs, PDF libraries, or database details. Application services orchestrate use cases through ports. Adapters implement those ports.

Recommended feature layout:

```
src/main/java/com/buses/examen/Progra/
  <feature>/
    domain/                 # Entities, value objects, enums, domain invariants, domain exceptions
    application/            # Use cases/application services, commands/results, transaction boundaries
      port/in/              # Inbound use case interfaces, e.g. PurchaseTicketUseCase
      port/out/             # Outbound ports, e.g. CustomerRepositoryPort, PdfReceiptPort
    adapter/
      in/web/               # Controllers + web DTOs; never expose JPA entities
      out/persistence/      # Spring Data/JPA adapters and persistence mappers
      out/pdf/              # PDF receipt generation adapter
      out/security/         # Session/security adapter details when feature-specific
    exception/              # Optional adapter/application exceptions if not domain-specific
  config/                   # Shared Spring Security, OAuth2, persistence, and wiring config
```

For small changes, do not over-engineer: a model-only change may include only `domain/` and focused tests. Add application ports/adapters only when implementing actual use cases.

Application services must be stateless. Use constructor injection with `private final` fields. Never expose JPA entities through the API — always map to DTOs at the web adapter boundary.

### Layer Model

Keep the layers explicit and do not blur responsibilities:

| Layer | Responsibility | Must not do |
| --- | --- | --- |
| `domain` | Business concepts, invariants, entities/value objects, domain exceptions | No Spring MVC/Security, no repositories, no PDF libraries, no HTTP DTOs |
| `application` | Use-case orchestration, transactions, commands/results, port definitions | No framework-specific persistence/web code, no direct PDF library calls |
| `adapter/in/web` | HTTP controllers, request/response DTOs, validation, authenticated principal mapping | No business rules beyond input validation |
| `adapter/out/persistence` | Spring Data/JPA repositories, persistence adapters, entity mapping details | No use-case orchestration |
| `adapter/out/pdf` | Concrete electronic receipt/PDF generation | No purchase rules or persistence decisions |
| `config` | Spring wiring, security, OAuth2/session configuration, bean composition | No domain logic |

If a class is hard to place in one layer, stop and redesign. Architecture is not decoration; it is how we keep the code understandable.

### Traditional Layer Names vs Hexagonal Placement

The project may use familiar Spring names, but they must map cleanly to hexagonal responsibilities:

| Familiar name | Hexagonal placement | Rule |
| --- | --- | --- |
| `model` / entity | `domain/` | Owns domain data and invariants. Do not inject services/repositories/controllers. |
| `repository` | `application/port/out/` for interfaces; `adapter/out/persistence/` for Spring Data/JPA implementations | Application code depends on repository interfaces/ports, not concrete persistence classes. |
| `service` | `application/` for use-case services; domain behavior stays in `domain/` | Services orchestrate use cases and transactions; they should depend on interfaces, not concrete adapters. |
| `dto` | `adapter/in/web/` for web DTOs; `application/` may use command/result records | DTOs must not leak into domain. Controller DTOs are adapter contracts. |
| `controller` | `adapter/in/web/` | Translates HTTP/session input into use-case calls; no business rule ownership. |

Prefer interfaces at boundaries. For example, `PurchaseTicketUseCase` is an inbound interface used by controllers, and `TicketRepositoryPort`/`ReceiptPdfPort` are outbound interfaces used by application services. Concrete classes such as Spring Data repositories, PDF generators, or security/session adapters implement those interfaces in `adapter/out/...`.

Do not make application services depend directly on normal concrete classes when the dependency crosses a boundary. Depend on ports/interfaces so the domain/application core stays replaceable and testable.

### Hexagonal Boundary Examples

- Buying tickets: `sales.application.port/in/PurchaseTicketUseCase` orchestrates customer lookup/registration, service availability, ticket code generation, payment/card handling, receipt PDF emission, and persistence through outbound ports.
- Routes and schedules: route/service domain owns schedule and price invariants; persistence adapters load/store them.
- Sessions: security/session configuration belongs in `config/` or `adapter/out/security`; controllers should rely on authenticated principals, not implement authentication logic.
- PDF receipts: application layer depends on a `ReceiptPdfPort`; concrete PDF library usage stays in `adapter/out/pdf`.
- Preloaded data: choose one explicit strategy per change (`data.sql`, migration tool, or an initializer). Do not maintain duplicate seed sources.

## Security

The service runs as an **OAuth2 Authorization Server**. When adding endpoints, consider whether they require token-based authentication and apply Spring Security rules explicitly rather than relying on defaults.

The assignment requires session control for registered users. If implementing browser/session flows, do not disable CSRF globally. If implementing a stateless API, document and enforce the stateless scheme explicitly.

## Coding Standards (Active Skills)

Skills in `.claude/skills/` are auto-loaded by context. Key rules:

- **Naming**: `PascalCase` classes/records, `camelCase` methods/fields, `UPPER_SNAKE_CASE` constants
- **Immutability**: favor records and `final` fields; no setters on domain objects
- **Optional**: `findBy*` methods return `Optional<T>`; use `.map()/.orElseThrow()`, never `.get()`
- **Exceptions**: domain-specific unchecked exceptions (e.g., `BusNotFoundException`); no broad `catch (Exception e)`
- **Logging**: SLF4J via `LoggerFactory.getLogger(...)`, parameterized messages, never string concat
- **Null**: `@NonNull` by default; use Bean Validation (`@NotNull`, `@NotBlank`) on DTO inputs
- **Javadoc**: public and protected members must have Javadoc; use `@param`, `@return`, `@throws`

### Clean Code Expectations

- Keep classes small and cohesive; one clear reason to change per class.
- Keep methods short, intention-revealing, and named after the business action they perform.
- Prefer explicit domain names from the assignment (`Compra`, `Ticket`, `Servicio`, `Ruta`, `Cliente`) over generic names like `Manager`, `Helper`, or `Processor`.
- Avoid duplicating business rules; centralize invariants in the domain or application use case that owns them.
- Avoid magic values; promote limits such as max tickets and purchase-window days to named constants.
- Do not leak adapter details inward: no controller DTOs in application/domain, no Spring Data interfaces as application dependencies.
- Prefer simple code over clever abstractions. Add patterns only when they protect a real boundary.

## Testing

Stack: JUnit 5 + AssertJ + Mockito. Use test slices:

The `pom.xml` uses Spring Boot 4 focused `*-test` starters (for example `spring-boot-starter-webmvc-test`, `spring-boot-starter-data-jpa-test`, and related modules). These are valid Spring Boot 4 artifacts; do not replace them with Spring Boot 3-style assumptions unless Maven resolution proves a problem.

- `@WebMvcTest` for controllers (no full context)
- `@DataJpaTest` for repositories
- `@SpringBootTest` for integration tests — prefer Testcontainers when a test actually needs a real database

No hidden sleeps, no partial mocks, no randomness without a fixed seed.
